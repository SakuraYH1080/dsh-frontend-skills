# 二次元角色与界面的空间融合（frontend-anime-fusion）

这个 skill 只做一件事：**决定角色立绘和界面在同一个空间里谁在前、谁在后、谁让位、谁裁切**。

它不画角色，也不决定页面风格。它回答四个问题：角色站在哪、界面挡住角色哪里、角色挡住界面哪里、屏幕变小时谁先让。**二次元界面做砸，九成不是图不好看，是角色和界面没有共享同一个空间坐标系**——角色贴在背景上，面板浮在角色上，两者从不互相遮挡，于是看上去像 PPT 里插了张图。

## 一、什么时候用 / 不用

**用**

- 页面以一张角色立绘为主体，界面元素（导航、按钮、信息面板、对话框）要和它共存一屏。
- 角色展示页、游戏启动器、个人主页、活动落地页、抽卡 / 图鉴 / 角色详情页。
- 视觉小说式对话界面：立绘 + 对话框 + 选项，三者要读出纵深。
- 已有页面「角色像贴纸」：面板永远压在脸正中、角色永远踩在底边、滚动时角色和背景一起动、移动端把头裁掉。
- 需要在同一套参数下产出桌面横屏与手机竖屏两个版本。

**不用（交给谁）**

- 主角是**材质**而不是角色：玻璃浮层、模糊、折射。交给 `frontend-liquid-glass`。本 skill 只借用它的不透明度数值关系，不生产玻璃参数。
- 主角是**运动的粒子 / 星尘 / 流体背景**：交给 `frontend-particles`。角色身后的氛围层只允许静态渐变与 SVG。
- 要有**苹果式的留白叙事与滚动节奏**（大标题、逐屏揭示、极简排版）：交给 `frontend-apple-minimal`。本 skill 的留白是为角色让位，不是为了叙事呼吸。
- 是**工业控制台 / HUD / 高密度操作台**（切角、编号、单色强调、数据栅格）：交给 `frontend-industrial-sci-fi`。把立绘塞进 HUD 会两边都失真。
- 请求本身就是**本 skill**（`frontend-anime-fusion`）：它不是别的东西的备胎。三种关系模型一个都不成立（角色只是列表缩略图、不参与空间）时，图片按普通内容图处理，不走本流程。
- 只是要**换一张更好看的立绘**：这是素材问题，不是空间问题。先按 `references/60-copyright.md` 确认来源，再谈构图。

上面五条是默认边界。用户明确要求组合时，组合才发生，且必须指定一个主导语言：空间坐标系、层级、遮挡与禁区归本 skill；frontend-particles 只能做角色身后的静态氛围替代（且不接管背景层），frontend-liquid-glass 只能给人物的信息面板加一层材质。一旦粒子或玻璃开始决定角色站在哪一层，主导权就交了出去，退回不用。

## 二、核心原则与硬边界

### 原则 1：角色是空间中的一个实体，不是图层上的贴图

判定一个页面是否真的「融合」，看三件事，缺一件就退回背景贴图：

| 判据 | 合格 | 不合格 |
| --- | --- | --- |
| 互相遮挡 | 至少一处「角色挡住面板」或「面板挡住角色」的明确边界 | 角色永远在面板之下或之上，从不交叉 |
| 共享光源 | 角色受光方向 = 背景光源方向 = 面板高光方向 | 角色自带顶光，背景是左下光 |
| 共享尺度 | 角色足部 / 裁切线与地面线、面板底边在同一透视里 | 角色像从另一个相机拍进来 |

**判据**：一处交叉遮挡 + 一个共同光源方向 + 一条共同基线，三者齐了才叫融合。

### 原则 2：关系模型先定，参数后调

三种模型不是风格选项，是**结构决策**，代价差一个数量级。定错模型，后面所有参数都在补一个补不上的洞。

| 模型 | 结构 | 适用 | 实现代价 | 辨识度 |
| --- | --- | --- | --- | --- |
| A 角色在界面之后（背景层） | 角色 z=0 < 面板 z=10，面板半透明或留缝 | 信息为主的详情页、个人站、设置页 | 低：两套图 + 一个 z-index | 低，容易像贴图 |
| B 角色穿透界面（跨层） | 同一张立绘切成前后两片：后片 z=0、前片 z=20，中间夹面板 z=10 | 启动器、活动页、抽卡 | 高：两套裁切路径 + 两片严格对齐 | 最高，一眼记住 |
| C 角色在界面之内（内容块） | 角色是 `figure`，面板不与它重叠，只做邻接 | 团队页、图鉴网格、文章头图 | 最低：普通流式布局 | 中，靠排版取胜 |

**判据**：模型 B 的唯一验收线是「缩放窗口时两片不脱开」——前片与后片必须由同一组 `--af-char-*` 变量驱动；任一片出现魔法数字就是错的。

### 原则 3：脸是禁区的原点

面板压脸是最常见的返工原因，因为它不是审美问题，是**遮挡了唯一的识别信息**。

禁区 = 角色头部矩形：宽 = 角色显示宽的 62%，高 = 角色显示高的 26%，上边从头顶留白下沿起算。面板与禁区的相交面积必须为 0；情绪性遮挡（对话框、气泡）允许 ≤ 8%，且只压下巴以下。

**判据**：把角色容器与所有面板的 `getBoundingClientRect()` 打出来，头部矩形与面板矩形的交集宽度 > 0 就退回。

### 原则 4：每一层只能做一件事

四层结构，层数写死，不许临时加第五层救场：

| 层 | z-index | 只负责 | 禁止 |
| --- | --- | --- | --- |
| L0 背景环境 | 0 | 色块、渐变、远景剪影 | 放角色、放正文 |
| L1 角色 | 10 | 立绘本体 + 边缘光 | 放可点击控件 |
| L2 界面面板 | 20 | 所有文字、按钮、输入 | 用 `backdrop-filter` 再造第二层材质 |
| L3 前景氛围 | 30 | 光斑、花瓣、不超过 3% 屏高的浅景深遮挡 | 覆盖文字、拦截指针 |

**判据**：任意一个可见元素都能被指认属于哪一层；指认不出来就是层结构坏了。

### 原则 5：可读性由 scrim 保证，不由「这张图够暗」保证

立绘的亮度由画师决定，你改不了；文字的对比度由你决定。所以文字永远坐在一个有确定不透明度的 scrim 上，且这个不透明度是**算出来的**，不是调出来的。

**判据**：正文与合成背景的对比度 ≥ 4.5:1，且要在角色图**最亮 1%** 与**最暗 1%** 两种情况下都成立。

### 原则 6：动效只允许发生在合成层

角色是页面上最大的位图，任何触发重排或重绘的动画都会掉帧。允许动画的属性只有 `transform` 与 `opacity`；`width / height / top / left / filter / mask-position` 一律不动画。

**判据**：DevTools 的 Paint flashing 打开，滚动与入场期间不出现覆盖角色区域的大面积重绘。

**硬边界**：本 skill 只决定角色立绘与界面的空间关系、分层与裁切。工业 HUD、苹果式留白叙事、玻璃材质参数、粒子算法不在职责内，即使它们能让画面更华丽。

### 一票退回

- 任一页面板与头部禁区相交面积 > 0。
- 角色占屏高 > 80% 或 < 45%：前者裁掉信息，后者变成缩略图。
- 头顶留白 < 5%：任何 `object-fit: cover` 都会切到头发。
- 角色与背景没有共同光源方向，且没有任何一层做色彩统一。
- 模型 B 的前后两片在 1280 / 1440 / 1920 三个宽度下出现 ≥ 2px 错位。
- 正文直接压在角色花纹或脸上，没有 scrim。
- 用 `mix-blend-mode: screen` 把角色「融进」背景，导致角色整体发灰、失去固有色。
- 入场时角色与面板同时出现（无错开），观感退化为「页面加载完成」。
- 素材来源未记录，或声称拥有角色版权。

## 三、可调参数与设计变体

九个旋钮的完整定义（单位、范围、越界症状）在 `references/10-composition.md`，数值唯一权威是 `assets/tokens.json`。这里是骨架：

1. `--af-char-h` 角色显示高 / 视口高（%），范围 45–80，默认 62
2. `--af-headroom` 头顶留白 / 角色显示高（%），范围 5–16，默认 10
3. `--af-anchor-x` 角色水平锚点（%），常用 33.3 / 38.2 / 61.8 / 66.7
4. `--af-gaze` 视线朝向（`left` / `right` / `front`），决定文字落哪一侧
5. `--af-scrim` 文字承载层不透明度（0–1），由对比度算例反解，默认 0.72
6. `--af-panel-gap` 面板与角色轮廓的最小间距（px），默认 24
7. `--af-edge-glow` 抠图边缘 1px 内发光强度（0–100%），默认 60
8. `--af-parallax` 角色相对背景的滚动位移比（0–1），默认 0.45
9. `--af-breath` 呼吸位移幅度与周期（px / s），默认 `2px / 4s`

**四套预设**

| 预设 | 关系模型 | char-h | headroom | scrim | 动效 | 场景 |
| --- | --- | --- | --- | --- | --- | --- |
| `stage` 立绘舞台 | A 之后 | 68% | 10% | 0.72 | 完整 | 角色展示页、图鉴详情 |
| `launcher` 启动器 | B 跨层 | 74% | 8% | 0.78 | 完整 | 游戏启动器、抽卡 |
| `profile` 个人站 | C 之内 | 48% | — | 0.00 | 轻量 | 个人主页、团队介绍 |
| `campaign` 活动页 | B 跨层 | 62% | 12% | 0.82 | 完整 + 前景 | 活动落地页、版本宣传 |

**变体卡格式**（写在交付说明开头三行，缺一行退回）：

```text
关系模型: B 跨层 | 预设: launcher | 裁切安全区: object-position 50% 12%
```

一套产品只用一套预设 + 一个变体差异。同时用两套预设，角色尺度会互相打架。

## 五、执行流程

1. **判定模型**：先问「角色要不要被面板挡一次」。要 → B；只做背景 → A；角色只是内容之一 → C。答不出说明信息结构还没想清。
2. **定量**：按预设定 `char-h` 与 `headroom`，角色容器高度写成 `calc(var(--af-char-h) * 1vh)`，不许手写固定像素。
3. **立坐标系**：`anchor-x` 定角色中心线，同时定文字块的列宽上限（视线反侧 ≤ 52%）。
4. **切层**：按四层结构建档；模型 B 额外产出「前片」容器，两片共用同一组变量。
5. **清禁区**：画出头部矩形，把所有面板挪出它；挪不动就改模型或缩面板，不许「半透明压一下」。
6. **配光**：给角色加与背景同向的 1px 内发光或描边，再叠一层背景主色 6–12% 的柔光。
7. **算 scrim**：按 `references/50-a11y-responsive.md` 的公式反解 α，在最亮 / 最暗两种背景上各验一次。
8. **编排动效**：角色先、面板后错开 120–200ms；呼吸 ±2px / 4s；视差位移系数恒 < 1.0（A 0.45 / B 0.85 / C 0 / 前景 1.6）。只用 `transform` / `opacity`。
9. **过响应式**：写出 360 / 768 / 1280 / 1920 四个宽度的 `object-position` 与重排规则。
10. **落版权记录**：来源、授权类型、可商用与否、署名文本四项，缺一项不算交付。

## 六、交付检查清单

- [ ] 交付说明开头有变体卡三行（关系模型 / 预设 / 裁切安全区）。
- [ ] 关系模型是 A / B / C 中明确的一个，并能指出至少一处交叉遮挡。
- [ ] 角色显示高在 45–80% 之间（给出实际值）。
- [ ] 头顶留白在 5–16% 之间（给出实际值）。
- [ ] 所有面板与头部禁区的相交面积为 0（给出 `getBoundingClientRect()` 两组数字）。
- [ ] 正文对比度在最亮与最暗背景上都 ≥ 4.5:1（给出两个实测值）。
- [ ] scrim 不透明度能由公式反推，不是手调值。
- [ ] 角色、背景、面板光源方向一致（写出一句话：光从哪个方向来）。
- [ ] 入场面板相对角色延迟 120–200ms（给出毫秒数）。
- [ ] 呼吸位移 ≤ 2px、周期 4s；视差位移系数 < 1.0 并给出实际值（A 0.45 / B 0.85 / C 0 / 前景 1.6）。

- [ ] 动画属性只有 `transform` 与 `opacity`（grep 一遍 CSS 可验）。
