# 50 · 验收矩阵、演练与交付卡

> 收尾时读。九行矩阵是底线，四步演练是流程，三个误判是复查表。

## 1. 九行验收矩阵

| # | 维度 | 怎么造 | 通过判据 |
| --- | --- | --- | --- |
| 1 | 明暗极端 | 纯白 / 纯黑 / 黑白条纹 / 运动亮斑四种背衬 | 正文 ≥ 4.5:1；条纹下文字周围仍有稳定底；亮斑扫过时不出现瞬时不可读 |
| 2 | 构图 | 320 / 390 / 768 / 1440 四档；超长标题；浏览器放大 200% | 脸与动作区可辨、无遮挡、无横向裁切；内容不被角色挤出可视区 |
| 3 | 主题竞争 | A 显示中，连选 B、C，B 的回调故意做慢 | 最终显示 C；B 的迟到回调不替换任何东西；中间无空屏 |
| 4 | 玻璃退出 | 开关子包；或把某面切回实底；再切回 | 入口与任务完整；样式节点被清理（计数回到基线）；不残留半透明遮罩 |
| 5 | 角色退出 | 关角色 / 模拟运行时缺失 / 手势中途中断 | 工具栏能进同一功能；取消不产生开合；提交最多一次 |
| 6 | 状态诚实 | 暂停 / 页面隐藏 / 传输停滞 / 解码失败 | 四种原因文案可区分；有效画面与恢复动作对应；不共用同一个转圈 |
| 7 | 资源 | 连续换场景 20 次；关开设置 10 次；等待空闲 | 渲染器 / 监听器 / 定时器数量回到预期规模，不随次数线性增长 |
| 8 | 偏好 | 拖完刷新；导入无效 JSON；A→B→A 主题往返 | 校验失败时保持先前状态；外观与已读记录分别保存、互不覆盖 |
| 9 | 输入 | 纯键盘；触摸；减少动态；减少透明度；强制颜色 | 任一模式下都能完成同一任务；焦点可见；无仅靠颜色传达的状态 |

## 2. 四步演练（照这个顺序跑）

### 第一步：真读数

1. 标记一条笔记已读。
2. 把工具面的遮罩候选降到 0.60，比较"白底理论估算"与"实际观感"。
3. 换条纹探针：模糊改的是背后细节，遮罩改的是文字底面——两者要分开看。

**产出**：一行可复核的记录（面 / 参数 / 背衬 / 对比度 / 取样点）。

### 第二步：慢成功连切

1. 把一个场景的加载人为拖慢。
2. 点 A，等它显示；再点 B。
3. 观察：屏幕先保留 A；B 有可交接画面后才切换。
4. 再把档位限制为"仅海报"和"仅纯色"各跑一次，比较状态提示与任务连续性。

**产出**：交接时序记录 + 三种档位下的文案。

### 第三步：拉绳与入口

1. 下拉角色：移动时只更新位置与提示。
2. 达到阈值后松手才开面板；再拖一次向上关。
3. 用 Enter / Space 走同一路径。
4. 关掉角色：工具栏入口仍可进设置；模态关闭后焦点回到可用的那个入口。

**产出**：手势状态表实测（idle → armed → previewing → committing → idle）+ 等价入口矩阵。

### 第四步：暂停、减少动态与偏好往返

1. 暂停场景，或打开系统"减少动态"。
2. 改一个背景，导出偏好。
3. 核对导出的 JSON 只含声明的字段（不含运行事实）。
4. 改一个合法设置后导入，等交接完成再刷新，看外观与已读记录是否都在。

**产出**：导出样本 + 刷新前后对照。

## 3. 三个误判（以及正确做法）

### 误判一：玻璃不清楚，就加模糊

现象：正文发灰、边缘糊。直觉是 `blur` 不够。

实际：模糊越强，背后细节越平均，面板整体越接近一层灰；文字对比并没有上升。

正确顺序：
1. 用黑白条纹看边界——分不清边界说明是**覆盖度不足**，不是模糊不足。
2. 用纯白算最坏叠合——白底之上再叠白，对比必然掉。
3. 改：阅读底色、文字色、材质分区（把正文搬到更实的面上）。

### 误判二：吉祥物很热闹，但它成了唯一入口

现象：功能都在，可用户关掉角色后找不到设置。

正确做法：把"打开设置"列成等价动作矩阵（指针 / 键盘 / 角色隐藏后），三列都要通。同时把两类信号分到不同通道：预览的连续事件一路，开合的单次提交一路。

### 误判三：切换闪黑，就延长淡入

现象：换场景时黑一下。直觉是把过渡拉长掩盖。

实际：黑的原因是"新层还没内容就开始显示"。拉长淡入只是把黑屏变得更长、更柔和。

正确做法：先测量"新画面第一帧何时真正可用"，再决定交接时机。三条正当路径：
1. 旧层继续显示，直到新层可交接。
2. 新层的海报先到，先上海报再上完整画面。
3. 明确进入纯色档，并告诉用户当前是降级形态。

## 4. 资源计数怎么做

```js
// 只在开发环境跑
const c = { raf: 0, timers: 0, listeners: 0 };
const raf = window.requestAnimationFrame;
window.requestAnimationFrame = (fn) => { c.raf++; return raf(fn); };
// 记录基线 → 操作 20 次 → 再记一次 → 比较
```

**判据**：操作 20 次后，活跃动画循环、未清理定时器、重复注册的监听器数量应回到基线 ±1，而不是随次数增长。

采样要求：至少覆盖三段常见任务，比较 p95 帧时与"连续掉帧"次数，而不只看平均帧率。

## 5. 交付卡（八行）

| # | 要填什么 |
| --- | --- |
| 1 | 用户此刻要完成的任务（一句话 + 完成判据） |
| 2 | 场景 / 表面 / 角色 / 氛围各自职责，以及关闭后剩下什么 |
| 3 | 内容安全区与脸部安全区：桌面、手机各一张 |
| 4 | 两个背衬极端下的文字对比度，以及取样位置 |
| 5 | 外观偏好 / 当前能力 / 业务状态分别归属哪一类数据 |
| 6 | 首帧、暂停、取消、失败、回退、重试的先后顺序 |
| 7 | 每个增强模块的挂载、让位、销毁、恢复 |
| 8 | 三项跨层回归、测试环境、仍然待验证的范围 |

**第 8 行必须诚实**：没测过的写"未验证"，不要写"应该没问题"。
