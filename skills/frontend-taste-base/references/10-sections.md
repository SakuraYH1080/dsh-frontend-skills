# 10 · 一节多高：节盒子与内容窗口表

这份文件解决一个问题：**这一页分成几节，每节多高。**
读完你应该能直接写出 section 的 CSS，并且知道某段内容该进哪一节、该不该拆。

---

## 1. 节盒子：唯一合法的写法

```css
main > section,
footer.closing {
  height: calc(var(--h, 1) * 100svh);
  display: grid;
  align-content: start;          /* 顶对齐，永不垂直居中 */
  padding-top: var(--padt);
  padding-bottom: var(--padb);
}
```

`--h` 只允许两个值：`1` 或 `2`。写在元素的行内样式或页级 CSS 里，不写在媒体查询里批量改（唯一例外见第 6 节平板）。

### 1.1 四条禁令

| 写法 | 为什么禁 |
| --- | --- |
| `min-height: 100vh` | 内容一多就把节撑高，节高从"定值"变成"随内容"，整页节奏失效 |
| `100dvh` | 地址栏收起/展开时值会变，滚动过程中节高跳变，表现为"滚到一半页面抖一下" |
| 脚本设 height | 与 CSS 的 svh 基准不同步，且在 resize 时抖动 |
| 出现第三节（`--h:3`） | 两屏已经是耐心上限。三屏的节读者会滚到一半就不知道自己在哪 |

### 1.2 为什么用 `svh` 不用 `vh`

`100vh` 在移动端等于"地址栏隐藏时的视口高"，比实际可见区域高。用 `100vh` 做的满屏节，在手机上底部一截永远被地址栏压住。

`100svh` 取"地址栏显示时的高度"，是**最小可见高度**。用它可以保证整节永远看得见。代价是当地址栏隐藏时，节底下会多出一条背景色——这比被压住一截好。

### 1.3 为什么是 `align-content: start`

节内容永远从 `--padt` 处开始，不居中。

垂直居中是一个看起来很安全、实际上很危险的选择：它让节高变化时内容位置也跟着变，读者每次滚动都要重新定位眼睛。顶对齐则相反——不管节多高，第一个内容永远在同一个位置，读者知道往哪看。

另一条：**每节只有一个 `h2`，且它是节的第一个内容。** 如果一节里有两个平级标题，那不是一节，是两节被硬塞进了一个盒子。

## 2. 内容窗口表（1440×900）

一屏 900px，减去 `--padt: 120` 与 `--padb: 72`，**可视内容区是 708px**。

先量内容：把这一节所有内容（标题、正文、图、按钮、卡片）按设计稿纵向堆起来，得到高度 `c`。

| c 的取值 | 判定 | 做法 |
| --- | --- | --- |
| c < 360 | 太空 | 合并进上一节，或补内容到 495 以上 |
| 360 ≤ c < 495 | 一屏，但有风险 | 一屏可以，但必须配一张图或一个大数字当视觉锚点 |
| 495 ≤ c ≤ 708 | 一屏，合格 | `--h: 1` |
| **708 < c < 1320** | **非法** | 砍到 708，或拆成两节，或用两栏吃掉高度 |
| 1320 ≤ c ≤ 1608 | 两屏，合格 | `--h: 2` |
| c > 1608 | 超了 | 拆成两节以上 |

### 2.1 两屏的上界是怎么来的

两屏可视区 = 708（第一屏内容）+ 900（第二屏整屏）− 300（第二屏首尾留白，因为整节只有一次 `--padt` 与一次 `--padb`）≈ 1308，取整 **1320**。

上界 1608 = 1320 + 288，即两屏内容再多 288px（约三分之一屏）以内仍算合格，超过就必须拆。

### 2.2 非法带的三种修法

**砍**：把多余内容删掉。优先删"再解释一遍"的段落、第三个功能卡、第二条证言。这一条最常被跳过，但它是对的——大多数页面内容比需要的多 30%。

**拆**：在主张切换的地方切开，每节各补足到 495 以上。注意拆完不能出现「360–495」的瘦节，那样两节都很虚。

**两栏**：把一段纵向堆叠的内容改成 `grid-template-columns: 1fr 1fr`，高度直接减半。适用于"并排的三条证据""左右对照的图与文"。

### 2.3 fill 值

`fill = c / 节高`。**下限 0.55。**

一节 708px 的内容区里只放了 300px 内容，fill = 0.42，读者会觉得"这一屏没加载完"。修法是补内容或删节。

上限不设。写满到 708 的节是好的。

**例外：footer.closing 不参与 fill 下限。** 收尾节只承担两件事——一句签名加一行法务/版权。它的 fill 天生在 0.20–0.30，硬抬到 0.55 只能靠注水，反而破坏收束感。closing 的判据换成：整节高度不超过 0.55 × 视口高，且签名那句话独处一行、法务行距签名 ≥ 64px。同理，页尾的 `<footer>` 若被写成正常 section 的内容量，说明内容没归位，该把内容退回到上一节。

**另一条例外：`--h` 大于 1 的 sticky 节（pin 型叙事节）。** 这类节的高度是「视口高 × h」，内容里有一部分是滚动过程中才进入视口的。量 fill 时要按 `inner / h` 而不是整节高去算，否则 h=2 的节会被误判为偏空。

## 3. 中文内容的估高换算

设计稿常用英文文案估高，中文字数一多就爆。经验换算：

| 元素 | 英文估法 | 中文换算 |
| --- | --- | --- |
| h1（两行，80px） | 2 × 88 = 176 | 同高。中文两行同样占 176，但字数只有英文一半 |
| h2（一行，40px） | 48 | 56（中文行高比英文大） |
| 正文一段（3 行，17px/1.6） | 82 | 中文 17px/1.8 三行 = 92；同一段中文通常 2–3 行，取 92 |
| 正文一段（中文约 80 字） | — | 按栏宽 32 字算，约 3 行 = 92 |
| 标签行（13px） | 20 | 22 |
| 按钮（44px 高） | 44 | 44（高度不变，只改左右内距） |

**估高规则**：中文每行按 32 字计（见 40-type-cn.md），行高按 1.8 计，则一行 ≈ 字号 × 1.8。

一条实操建议：**先写好中文文案，再估高。** 用英文占位符估出来的高度，换成中文后普遍高 15%–25%，直接掉进非法带。

## 4. 六档的节清单模板

每档给一个默认节序，可以增删，但不能改节的内部结构。

### software（App / SaaS / 开发者工具）

1. hero：产品在做什么，一句话 + 一个真实界面截图
2. 能力：三个具体动作，每个配一个界面片段
3. 差异：一件别人做不到的事，配对比
4. 证据：一个数字或一条客户原话
5. 定价或试用
6. closing

6 节，全 `--h:1`。

### gaming（游戏）

1. hero：游戏名 + 类型 + 发布行，全出血 key art
2. 世界观：一张大图 + 两三句
3. 玩法：三个机制，每个配动图或截图
4. 平台与发售信息
5. closing

5 节。第 2 节可以 `--h:2`。

### tech（硬件 / 科技设备）

1. hero：设备本身按真实比例占满
2. 规格：参数表或三个关键数
3. 场景：一张实拍 + 一句说明
4. 兼容与生态
5. closing

5 节。第 2 节常配 `--h:2`。

### product（实体产品）

1. hero：产品大幅完整地立着
2. 细节：局部特写，每节一张
3. 使用场景
4. 规格
5. 购买
6. closing

6 节。产品页里**产品必须占满画幅大部分**，不能是灰底圆角面板里的中等尺寸。

### service（雇人的：诊所 / 律所 / 工作室）

1. hero：谁 + 在哪 + 做什么，配一张人像或空间照
2. 服务清单：五项以内，每项一句
3. 人：一张团队照 + 名字
4. 流程：三步
5. 联系方式与地址
6. closing

6 节。**照片主导，不用示意图。**

### place（人来的：咖啡馆 / 客栈 / 餐厅 / 健身房）

1. hero：是什么 + 在哪，用一张该场所的照片（异地场所用该地区风景）
2. visit：地址、时间、怎么来
3. 提供什么：菜单 / 房型 / 课程，2–4 项
4. 空间：两三张照片
5. 预订或到店
6. closing

6 节，**全页 12–20 张照片**（紧凑页 8–12 张，少于 8 张就做 3 屏短页）。
place 不使用 effect、不使用示意图、不使用循环动效，**radius 全部为 0 或 2px**。

## 5. 390 宽（手机）的换算

手机 390×844。可视内容区：

| 项 | 值 |
| --- | --- |
| `--padt` | 96 |
| `--padb` | 48 |
| 一屏内容区 | 464 – 700（减去浏览器 chrome 后取 464 保守值） |
| 两屏内容区 | 1268 – 1544 |

手机上同一个 CSS 不用改：`100svh` 自动适配。但有两件事必须改：

1. **`--gut` 从 80 降到 24**，否则内容区只剩 342px，一行放不下 20 个汉字。
2. **两栏改一栏**。`.g2` 在 640 以下必须塌成一栏，否则每栏 160px，中文一行 9 字，读不下去。

### 5.1 手机上的「一屏一节」会失效吗

不会，但会变紧。708 → 464，内容要砍掉三分之一。这是为什么 place 档在手机上的照片数量要减到 8–12 张。

如果一节在手机上装不下，处理顺序是：先删内容 → 再减图 → 最后才允许 `--h:2`。**不要为了保住内容把每个节都改成两屏**，那样在手机上滚十屏才看完三节。

## 6. 平板（640–1023）

判分尺寸取 768×1024 与 820×1180 竖屏。

| c 的取值 | 判定 |
| --- | --- |
| c ≤ 832 | 一屏 |
| 832 < c < 1130 | 砍到一屏 |
| 1130 ≤ c ≤ 1856 | 两屏 |

**页级 CSS 唯一允许的媒体查询**：

```css
@media (min-width: 640px) and (max-width: 1023px) {
  #problem-section { --h: 2; }
}
```

只允许改 `--h`，且必须按 id 单节改，不允许整页批量改。

### 6.1 一个实测过的坑

在 820 宽下，一个 480×688 的对比图放在自己的 `.hero__art` 里，被父级的折线（`clip-path` 或背景分界）切掉了下缘。

原因：平板上图片容器的高度由宽度按比例算出，但节高是固定的，两者在某个宽度下会冲突。修法是给图容器一个 `aspect-ratio` 上限，或把图放进有独立背景的块，不让它跨在背景分界线上。

## 7. 对齐：左右内容边缘

节内所有内容块的左右边缘必须对齐到 **wrap**（`max-width` 容器）。三条具体判据：

1. **`container-edges`**：文字左边缘、图片左边缘、卡片左边缘在同一条竖线上。允许图片出血，但不允许"图片比文字缩进 12px"这种无意识的错位。
2. **`split-pair`**：两栏布局里，左栏文字底部与右栏图片底部不必齐平，但**左栏起点与右栏起点必须齐平**。
3. **`right-edge`**：所有右边缘收在同一个 x 坐标。常见的破法是一个卡片比别的宽 20px，肉眼几乎看不出，但整页会显得"松散"。

---

## 8. 分离：不许用装饰

节与节之间、节内块与块之间，**只能用两种方式分离**：

- 整幅底色变化（`--g-main` ↔ `--g-alt` ↔ `--g-dark`）
- 留白

禁止：`border-top`、`box-shadow` 当分隔线、给每个块一个内嵌浅色背景、给每节加一条品牌色带（一页最多一条，且是收尾带）。

### 8.1 为什么这条这么重要

AI 生成页面的第一特征就是"每一块都要有个框"。因为模型在训练数据里看到大量卡片化设计，学会的是"内容 = 卡片"。结果是一页里有十二个白底圆角卡片，页面变成一堆盒子。

真实的好页面里，一页通常只有 0–2 个真正的卡片（用于并列的三项、一个浮起的浮层）。其余内容直接躺在地面上。

**检验方法**：数一下页面上有多少个 `background` 与 `border-radius` 同时非默认的元素。超过 6 个，页面已经盒子化了。

---

## 9. 滚动纪律

禁止：

- `scroll-snap`（节拍式吸附让读者失去控制感）
- 滚动劫持（`preventDefault` + 自定义滚动）
- 平滑滚动库（Lenis / locomotive 类）
- `scroll-behavior: smooth` 用于整页

允许：

- 在**单个节的盒子内**用 `position: sticky`（dealt moment），且只在该盒子内生效
- `IntersectionObserver` 触发一次性的入场

判据一句话：**读者滚多少，页面走多少。** 任何让这两者不成正比的实现都是错的。

## 10. 一票退回清单

出现任一条，这一页不算做完：

- [ ] 出现 `--h: 3` 或更大
- [ ] 用 `min-height` 撑节
- [ ] 某节有两个平级 `h2`
- [ ] 内容落在 708–1320 非法带且没处理
- [ ] 某节 fill < 0.55
- [ ] 节内有分隔线 / 投影当分隔 / 内嵌底色块
- [ ] 卡片化元素超过 6 个
- [ ] 用了 scroll-snap 或滚动劫持
- [ ] 手机端两栏没有塌成一栏
